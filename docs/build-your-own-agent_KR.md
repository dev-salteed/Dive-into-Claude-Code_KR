# 나만의 AI 에이전트 만들기: 설계 공간 가이드

> 이 문서는 코딩 튜토리얼이 아니다. 프로덕션 AI 에이전트 시스템을 구축할 때 반드시 내려야 하는 **설계 결정(design decision)** 에 관한 가이드이며, Claude Code의 아키텍처 분석에서 도출한 내용을 담고 있다.

모든 프로덕션 코딩 에이전트는 동일하게 반복되는 설계 질문에 답해야 한다. Claude Code는 그 질문들에 대한 하나의 답안일 뿐이다. 이 가이드는 결정 공간 자체를 지도처럼 펼쳐 보여, 여러분이 스스로 정보에 입각한 선택을 내릴 수 있도록 돕는다.

---

## 결정 1: 추론(Reasoning)은 어디에 두는가?

**핵심 질문:** 의사결정의 책임을 모델에 얼마나 맡기고, 하네스(harness) 코드에 얼마나 둘 것인가?

> **[번역 주석]** 하네스(harness)는 모델 주변을 감싸 입력·출력·도구 호출·안전 검증 등을 통제하는 운영 인프라 코드를 의미한다. 모델이 "두뇌"라면 하네스는 "골격과 신경계"에 해당한다.

| 접근 방식 | 사례 | 트레이드오프 |
|:---------|:--------|:----------|
| **최소한의 스캐폴딩(scaffolding)** | Claude Code (AI 로직 약 1.6%) | 모델에 최대한의 자율성을 부여하고, 하네스는 경계만 강제한다. 시간이 흐를수록 모델 능력이 향상된다는 데 베팅하는 전략이다. |
| **명시적 상태 그래프** | LangGraph | 개발자가 흐름을 통제하므로 디버깅과 예측이 쉽다. 그러나 모델을 제약하며, 모델 능력이 발전하면 그래프도 함께 업데이트해야 한다. |
| **무거운 계획 스캐폴딩** | Devin | 다단계 플래너 + 작업 추적기. 복잡한 워크플로에는 더 안정적이지만, 스캐폴딩 자체가 유지보수 부담이 된다. |

> **[번역 주석]** 스캐폴딩(scaffolding)은 본래 건설 현장의 "비계"를 뜻하며, 여기서는 모델이 작업을 수행할 수 있도록 보조하는 외부 골조(계획 단계, 상태 관리, 작업 트리 등)를 의미한다.

> **[번역 주석]** LangGraph는 LLM 워크플로를 상태 그래프 형태로 명시적으로 정의하는 프레임워크이고, Devin은 Cognition AI가 발표한 자율 소프트웨어 엔지니어 에이전트다.

**Claude Code에서 얻은 핵심 통찰:** 최첨단 모델(frontier model)들의 능력이 수렴함에 따라(SWE-bench 상위 3개 모델이 1% 이내 격차), **차별화 지점은 모델이나 스캐폴딩이 아니라 운영 하네스로 옮겨가고 있다**. 결정론적 인프라(컨텍스트 관리, 안전성, 복구)에 투자하는 편이 계획 제약을 추가하는 것보다 더 큰 신뢰성을 가져다줄 수 있다.

> **[번역 주석]** "frontier models"는 현재 기술 최전선에 있는 최상위 LLM들(예: Claude, GPT, Gemini의 최신 모델)을 가리키는 업계 용어다.

**스스로에게 물어볼 질문:**
- 목표로 하는 모델은 얼마나 유능한가? 모델이 유능할수록 스캐폴딩은 덜 필요하다.
- 워크플로가 얼마나 예측 가능해야 하는가? 규제 도메인에서는 명시적 그래프가 필요할 수 있다.
- 모델 능력은 얼마나 빠르게 향상되고 있는가? 모델이 스캐폴딩을 추월하면 무거운 스캐폴딩은 기술 부채가 된다.

## 결정 2: 안전 태세(Safety Posture)는 어떻게 잡을 것인가?

**핵심 질문:** 에이전트가 해로운 행동을 하지 못하도록 어떻게 막을 것인가?

| 접근 방식 | 사례 | 트레이드오프 |
|:---------|:--------|:----------|
| **거부 우선 + 다층 강제(Deny-first with layered enforcement)** | Claude Code (독립적인 7개 계층) | 매우 안전하지만 승인 피로(approval fatigue)를 유발할 수 있다(프롬프트의 93%가 검토 없이 승인됨). 점진적 신뢰(graduated trust) 메커니즘이 필요하다. |
| **컨테이너 격리(Container isolation)** | SWE-Agent, OpenHands (Docker) | 강력한 경계지만 입자도가 거칠다. 컨테이너 안에서는 모든 것이 허용되고, 밖에서는 아무것도 닿을 수 없다. |
| **VCS 롤백** | Aider (git 기반) | 가볍지만 파일 변경에만 보호 효과가 있다. 네트워크 요청, 데이터 유출, 셸 부수효과(side effect)는 막지 못한다. |
| **승인만 사용(Approval-only)** | 기본 챗봇 | 단순하지만 규모가 커지면 행동 측면에서 신뢰할 수 없다. 사용자는 곧 프롬프트를 읽지 않게 된다. |

> **[번역 주석]** "approval fatigue"란 사용자가 너무 많은 권한 승인 요청에 지쳐, 결국 내용을 읽지 않고 무비판적으로 "예"를 누르게 되는 현상을 가리킨다.

> **[번역 주석]** Aider는 로컬 git 저장소를 안전망으로 활용하는 오픈소스 AI 코딩 에이전트이고, OpenHands와 SWE-Agent는 Docker 컨테이너 기반의 학술/오픈소스 에이전트 프로젝트다.

**Claude Code에서 얻은 핵심 통찰:** 심층 방어(defense in depth)는 안전 계층들이 **서로 독립적인 실패 모드(failure mode)** 를 가질 때만 작동한다. Claude Code의 계층들은 토큰 비용이라는 경제적 제약을 공유한다. 즉, 하위 명령이 50개를 넘는 명령은 보안 분석 자체를 우회한다. 계층은 독립적으로 실패하도록 설계해야 한다.

**승인 피로에 대한 핵심 통찰:** 사용자는 권한 프롬프트의 93%를 승인한다. 해법은 더 많은 경고가 아니라 **재구성된 경계** 다. 즉, 자율 작동이 안전한 영역을 만들어주는 샌드박싱과 분류기다.

**스스로에게 물어볼 질문:**
- 여러분의 에이전트가 저지를 수 있는 최악의 일은 무엇인가? (운영 데이터 삭제? 이메일 발송? 코드 유출?)
- 사용자가 내려야 하는 결정 수를 줄이기 위해 샌드박싱을 활용할 수 있는가?
- 안전 계층들이 실패 모드를 공유하지는 않는가? (예: 모두 토큰 예산에 의존)

## 결정 3: 컨텍스트는 어떻게 관리할 것인가?

**핵심 질문:** 컨텍스트 윈도우(context window)는 유한하다. 모델이 무엇을 보게 할지 어떻게 결정할 것인가?

| 접근 방식 | 사례 | 트레이드오프 |
|:---------|:--------|:----------|
| **점진적 컴팩션 파이프라인(Graduated compaction pipeline)** | Claude Code (5개 계층) | 가장 많은 정보를 가장 오래 보존한다. 구현과 디버깅이 복잡하고, 압축은 사용자에게 보이지 않는다. |
| **단순 잘라내기(Simple truncation)** | 많은 기본 에이전트 | 구현이 쉽다. 그러나 잠재적으로 중요한 초반 컨텍스트를 잃는다. |
| **슬라이딩 윈도우** | 일부 채팅 애플리케이션 | 동작이 예측 가능하다. 그러나 무엇이 중요한지에 대한 의미론적 인식이 없다. |
| **RAG (검색 증강)** | 일부 IDE 통합 | 전체 코드베이스에 접근할 수 있다. 그러나 검색 품질이 병목이 되고, 검색된 청크는 주변 컨텍스트가 부족할 수 있다. |
| **단일 요약** | 일부 에이전트 | 한 번의 요약 패스. 그러나 단일 압축은 중요한 디테일을 잃을 수 있다. |

> **[번역 주석]** 컴팩션(compaction)은 대화 이력을 압축·요약·재구성해 컨텍스트 윈도우 안에 더 많은 의미를 담는 일련의 기법을 통칭한다.

**Claude Code에서 얻은 핵심 통찰:** 컨텍스트는 거의 모든 다른 아키텍처 결정을 형태짓는 **결정적 제약(binding constraint)** 이다. 지연 로딩(lazy loading), 도구 스키마 지연 노출, 서브에이전트(subagent)의 요약만 반환하는 정책, 도구 결과별 토큰 예산 모두 컨텍스트가 희소하기 때문에 존재한다. 첫날부터 컨텍스트 희소성을 전제로 설계해야 한다.

**점진적 접근법:** 가장 덜 파괴적인 압축부터 적용하라. 예산 축소(저비용) → 이력 다듬기(저비용) → 캐시 인지 압축(중간 비용) → 가상 프로젝션(중간 비용) → 전체 요약(고비용, 최후의 수단).

**스스로에게 물어볼 질문:**
- 컨텍스트 윈도우 크기는 얼마인가? 이 값이 압축의 공격성을 결정한다.
- 긴 세션(수 시간 작업)을 지원해야 하는가? 단일 패스 잘라내기로는 버틸 수 없다.
- "가이드용" 컨텍스트(지시문)와 "작업용" 컨텍스트(대화)를 분리할 수 있는가?

## 결정 4: 확장성(Extensibility)은 어떻게 다룰 것인가?

**핵심 질문:** 외부 도구, 커스텀 지시문, 사용자 커스터마이징은 시스템에 어떻게 결합되는가?

| 접근 방식 | 사례 | 트레이드오프 |
|:---------|:--------|:----------|
| **컨텍스트 비용에 따른 점진적 메커니즘** | Claude Code (hooks=0, skills=낮음, plugins=중간, MCP=높음) | 비용이 다른 확장 수단들. 관리가 복잡하지만 확장에는 강하다. |
| **단일 통합 API** | 다수의 도구 사용 프레임워크 | 이해하기 쉽다. 그러나 모든 확장이 컨텍스트를 소비하므로 확장성이 제한된다. |
| **플러그인 마켓플레이스** | IDE 확장 | 풍부한 생태계 가능성. 그러나 품질 관리와 보안 검토가 병목이 된다. |

**Claude Code에서 얻은 핵심 통찰:** 모든 확장이 컨텍스트 토큰을 소비할 필요는 없다. 훅(hook, 비용 0)은 컨텍스트 윈도우를 건드리지 않고 라이프사이클 이벤트를 처리한다. 스킬(skill, 저비용)은 관련 있을 때만 주입된다. 컨텍스트 비용이 높은 메커니즘(MCP)은 진정으로 새로운 도구 표면이 필요할 때만 사용하라.

**세 가지 주입 지점:** 모든 에이전트 루프(agent loop)에는 확장이 개입할 수 있는 세 곳이 있다.
1. **assemble()** -- 모델이 무엇을 보는가 (지시문, 도구 스키마)
2. **model()** -- 모델이 무엇에 닿을 수 있는가 (사용 가능한 도구)
3. **execute()** -- 행동이 실행되는지/어떻게 실행되는지 (권한 게이트, 사전/사후 훅)

**스스로에게 물어볼 질문:**
- 에이전트가 지원해야 할 도구는 몇 개인가? 도구가 많을수록 컨텍스트 압박이 커진다.
- 서드파티 확장이 필요한가? 보안과 품질 관리를 미리 계획하라.
- 모델이 도구를 실제로 필요로 할 때까지 도구 스키마 로딩을 지연시킬 수 있는가?

## 결정 5: 서브에이전트(Subagent)는 어떻게 작동하는가?

**핵심 질문:** 에이전트가 하위 작업을 생성할 때, 컨텍스트를 공유할 것인가, 아니면 격리해 실행할 것인가?

| 접근 방식 | 사례 | 트레이드오프 |
|:---------|:--------|:----------|
| **격리된 컨텍스트 + 요약 반환** | Claude Code (사이드체인(sidechain) 트랜스크립트) | 컨텍스트 폭증을 방지한다(약 7배 토큰 비용). 그러나 서브에이전트끼리 세밀한 상태를 공유할 수 없다. |
| **공유 컨텍스트** | 일부 멀티에이전트 프레임워크 | 정보 공유가 완전하다. 그러나 N개의 에이전트로 컨텍스트가 빠르게 가득 찬다. |
| **메시지 패싱** | 액터 모델 시스템 | 경계가 깔끔하다. 그러나 명시적인 프로토콜 설계가 필요하다. |

**Claude Code에서 얻은 핵심 통찰:** 서브에이전트 세션은 표준 세션 대비 약 7배의 토큰을 소비한다. 부모에게는 요약만 반환되며, 전체 이력은 부모 컨텍스트에 절대 들어가지 않는다. 이는 컨텍스트 절약을 위해 필수적이다.

**스스로에게 물어볼 질문:**
- 하위 작업들은 서로의 작업을 봐야 하는가?
- N개의 서브에이전트가 N × 컨텍스트_윈도우 토큰을 소비하지 않도록 어떻게 막을 것인가?
- 서브에이전트는 부모 권한을 상속받는가, 아니면 독자적으로 권한을 확립하는가?

## 결정 6: 세션은 어떻게 영속(Persistence)되는가?

**핵심 질문:** 세션이 끝나면 무슨 일이 일어나는가? 무엇이 다음 세션으로 이어지는가?

| 접근 방식 | 사례 | 트레이드오프 |
|:---------|:--------|:----------|
| **추가 전용(Append-only) JSONL** | Claude Code | 감사 가능하고, 재구성 가능하며, 단순하다. 그러나 질의 능력은 부족하다. |
| **데이터베이스** | 일부 엔터프라이즈 에이전트 | 풍부한 질의, 빠른 조회. 그러나 인프라 의존성이 추가되고 투명성이 떨어진다. |
| **무상태(Stateless)** | 대부분의 채팅 API | 가장 단순하다. 그러나 재개도, 분기도, 감사 로그도 없다. |

**Claude Code에서 얻은 핵심 통찰:** **재개 시 권한을 절대 복원하지 않는다.** 신뢰는 항상 현재 세션에서 다시 확립된다. 보안 상태는 세션 경계를 넘어 암묵적으로 영속되어서는 안 된다.

**감사 가능성(auditability)에 대한 핵심 통찰:** 추가 전용 JSONL은 모든 이벤트가 사람이 읽을 수 있고, 버전 관리가 가능하며, 특수 도구 없이 재구성될 수 있음을 의미한다. 질의 능력의 약간의 손실은 그 투명성에 비하면 충분히 감수할 만하다.

---

## 메타 패턴: 반복되는 세 가지 설계 원칙

여섯 개의 결정 전반에 걸쳐, Claude Code의 아키텍처에서는 세 가지 패턴이 반복적으로 나타난다.

1. **단일 메커니즘이 아닌 점진적 계층화** -- 안전성, 컨텍스트, 확장성 모두 단일 해결책이 아니라 독립적인 단계들을 쌓아 올리는 방식을 사용한다.

2. **질의 능력보다 감사 가능성을 우선하는 추가 전용 설계** -- 모든 것은 재구성될 수 있으며, 어떤 것도 파괴적으로 편집되지 않는다.

3. **결정론적 하네스 안에서의 모델 판단** -- 모델은 자유롭게 결정하고, 하네스는 경계를 강제한다. 1.6% / 98.4%라는 비율은 우연이 아니다.

> **[번역 주석]** 모델 능력이 빠르게 평준화되고 있는 시대에, 진짜 "moat"(해자, 즉 경쟁 우위)는 모델 자체가 아니라 그것을 둘러싼 운영 하네스에 있다는 것이 이 문서의 일관된 메시지다.
